# ADR 001: 语法糖与核心语法边界

## 状态

已接受（2026-07-31）

## 背景

Kore 强调"少而正交"，每个记号只有一个含义。但在实践中，部分构造可以视为其他构造的简写（语法糖），需要明确划定糖与核心语法的边界，以保证编译器实现的一致性和可预测性。

关键问题：
1. 哪些构造是"糖"（需要脱糖），哪些是核心 AST 节点？
2. 脱糖发生在哪个阶段（parse 前/parse 后/语义分析）？
3. 如何保证"糖"的行为与其脱糖目标完全一致？

## 决策

### 原则

1. **脱糖在 parse 前完成**：所有语法糖在词法/语法分析之前转换为核心语法，解析器只处理核心构造。
2. **唯一脱糖规则**：只有能在纯 token 级别（不依赖类型信息、不依赖作用域）完成的转换才允许作为 parse 前糖。
3. **需要语义信息的"糖"保留为 AST 节点**：在类型检查或代码生成阶段处理。

### 唯一的 parse 前语法糖

| 构造 | 脱糖目标 | 理由 |
|------|---------|------|
| `T?` | `T \| nil` | 纯 token 级别可完成，不依赖类型信息 |

### 保留为 AST 节点的构造

以下构造虽然在语义上可视为其他构造的简写，但因为需要类型信息、作用域信息或控制流分析，保留为独立 AST 节点，在语义层处理：

#### 操作符类

| 构造 | AST 节点 | 处理阶段 |
|------|---------|---------|
| `?.` | 独立双字符操作符 | 类型检查（短路求值 nil） |
| `:=` | 独立双字符 token | 类型推断（非脱糖，表示类型待推断的运行期绑定） |
| `\|>` | `Pipe(left, right)` | 类型检查（展开为函数调用） |
| `..` / `..=` | `Range(start, end, inclusive)` | 类型检查（一等类型 `Range[T]`） |

#### 错误处理类

| 构造 | AST 节点 | mode 枚举 |
|------|---------|---------|
| `expr!` | `ErrorHandle(expr, Propagate)` | 传播错误 |
| `expr!!` | `ErrorHandle(expr, Panic)` | 失败即 panic |
| `expr ?! default` | `ErrorHandle(expr, Default(fallback))` | 失败取默认值 |

错误集合并集推断在类型检查阶段完成。

#### 控制流类

| 构造 | AST 节点 | 备注 |
|------|---------|------|
| `?` 守卫 | `Guard(cond, body)` | 单臂早退，无穷尽检查 |
| `?` 条件链 | `CondChain(arms[])` | 多布尔臂，需要 `_` 兜底 |
| `? expr is` | `Match(expr, arms[])` | 模式匹配，联合类型穷尽检查 |
| `@ cond` / `@` | `CondLoop(cond?, body)` | 条件循环/无限循环 |
| `@ range =>` | `RangeLoop(range, binding, body)` | 范围循环，可静态确定次数 |
| `@ iter =>` | `IterLoop(iter, binding, body)` | 迭代循环，消费 `Iter` trait |
| `defer expr` | `Defer(expr)` | 作用域退出时执行，控制流分析在代码生成层 |
| `jmp f(args)` | `TailCall(func, args)` | 保证尾调用，无法完成时报错 |

`?` 和 `@` 各自的三种形态对应三个独立节点，语义规则差异明显（穷尽检查、迭代次数可预测性等）。

#### 函数与赋值类

| 构造 | AST 节点 | 备注 |
|------|---------|------|
| `\x => body` | `Closure(params, body)` | 捕获分析在语义层 |
| `a, b = b, a` | `ParallelAssign(lhs[], rhs[])` | 右侧全部先求值语义显式保留 |

#### 类型与转换类

| 构造 | AST 节点 | 备注 |
|------|---------|------|
| 裸值提升（`T` → `T?` / `T ! E`） | `Coerce(expr, target)` | 类型检查阶段插入，双向推断 |
| `expr as Type` | `Cast(expr, target)` | unsafe 判断在类型检查阶段 |
| `+%` / `+\|` / `-%` 等 | `BinOp(lhs, rhs, op, mode)` | mode 枚举 `Checked \| Wrapping \| Saturating` |
| `Vec3{x: 1.0, ..0}` | `StructInit(type, fields[], fill?)` | 类型检查阶段展开剩余字段 |
| `Vec[i32]` | `GenericApply(base, args[])` | 与 `[]i32` 切片明确区分 |

#### 修饰符与声明类

| 构造 | 处理方式 | 备注 |
|------|---------|------|
| `own ^T` / `own []T` | 修饰符，产出 `OwnPtr(T)` / `OwnSlice(T)` | 所有权标记，后必须跟 `^` 或 `[` |
| `~^T` / `~x` | 修饰符，产出 `MutPtr(T)` / 可变绑定 | 可变性标记，统一在所有位置 |
| `vol ^T` | 修饰符，产出 `VolPtr(T)` | volatile 语义，所有访问自动 volatile |
| `pub fn` / `pub T` | 声明节点的 `pub: bool` 属性字段 | 可见性标记，不改变结构 |
| `#packed` / `#align(N)` | `Attr(name, args[])` 附加在声明上 | 通用属性系统，可扩展 |
| `unsafe { }` | `Unsafe(block)` 独立节点 | 权限边界变更，便于静态分析 |

#### 导入与嵌入

| 构造 | AST 节点 | 位置 |
|------|---------|------|
| `use std.io` | `Import(path)` | 顶层，影响名字解析 |
| `use Base` | `Embed(type)` | 结构体/impl 内，影响类型布局与方法查找 |

#### 纯语法元素

| 构造 | 处理方式 | 备注 |
|------|---------|------|
| `is` | 纯语法引导符 | 只在 `Match` 节点中出现，不构成独立表达式 |
| `;` | 纯语法分隔符 | parse 后消失，块内语句序列由 `Block(stmts[])` 数组表达 |

### 横切关注点

#### 可变性检查

语义层统一的"可变性检查" pass，验证 `~` 标记的一致性：

1. 赋值左侧必须是 `~` 绑定
2. `~^T` 参数只接受指向 `~` 绑定的指针
3. `~^self` 方法只能在 `~` 绑定上调用

这是 `~` 在所有位置含义一致的核心保证。

#### 编译期求值

任意函数可在 `::` 上下文运行，编译器内置求值器执行。不限制纯函数，允许在编译期做类型计算、代码生成。这是自举编译器的真实需求。

## 后果

### 正面

1. **边界清晰**：只有一条 parse 前糖规则，编译器实现不会在"什么时候脱糖"上产生歧义。
2. **错误信息精确**：大多数构造保留为 AST 节点，类型错误可以精确指向原始构造（如"管道左侧类型与函数第一参数不匹配"），而非脱糖后的内部表示。
3. **工具链友好**：语法树保留用户书写的结构，IDE、格式化工具、静态分析工具可以直接操作源码对应的 AST 节点。
4. **语义一致性**：`T?` 脱糖后与 `T | nil` 共享完全相同的类型检查、穷尽匹配逻辑，不会出现双轨行为。

### 负面

1. **AST 节点数量增加**：相比激进脱糖策略，AST 定义更复杂（约 30+ 种节点类型）。
2. **类型检查器负担**：需要为每种"糖节点"实现语义展开逻辑（如 `Pipe` 展开为函数调用、`ErrorHandle` 推断错误集合并集）。
3. **代码生成复杂度**：部分节点（如 `ParallelAssign`、`Defer`）需要在后端生成特殊的临时变量或控制流结构。

### 取舍权衡

选择"少量 parse 前糖 + 大量语义层节点"的策略，优先保证：
- 用户可预测性（源码结构保留在 AST）
- 工具链可扩展性（AST 对应源码结构）
- 错误信息精确性（类型错误指向原始构造）

代价是编译器实现复杂度上升，但这符合 Kore"让编译器复杂、让用户简单"的设计哲学。

## 实现检查清单

编译器实现时需要验证以下不变式：

- [ ] `T?` 在 parse 前完全脱糖为 `T | nil`，解析器不产出 `Optional` 节点
- [ ] `?.` / `:=` / `|>` / `..` 等作为独立 token 被词法分析器识别
- [ ] `?` / `@` 根据上下文（是否有 `is`、是否有 `=>`）产出不同节点类型
- [ ] `ErrorHandle` 的错误集合并集推断在类型检查阶段完成，不影响 parse
- [ ] 裸值提升只在已知期望类型的位置发生（return、赋值给显式类型绑定）
- [ ] `~` 可变性检查覆盖所有赋值、参数传递、方法调用位置
- [ ] `own` / `vol` 只能修饰 `^T` 或 `[]T`，其他位置是语法错误
- [ ] `is` 只在 `Match` 节点中出现，作为独立表达式时报语法错误
- [ ] 通用属性系统 `#name(args)` 可附加到所有声明节点
- [ ] `Range[T]` 实现 `Iter` trait，可用于 `IterLoop` 节点
