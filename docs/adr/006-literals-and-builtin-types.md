# ADR 006 — 字面量与内置类型

**状态**: 已决定  
**日期**: 2026-08-02  
**关联**: ADR 001（语法糖边界）、ADR 002（表达式边界）、ADR 003（类型系统）、ADR 004（作用域与绑定）、ADR 005（控制流与模式匹配）

---

## 背景

本 ADR 固定 Kore 的字面量词法与内置类型集合。这一层是词法器和类型检查器的共同基础，此前散落在 `docs/spec/` 里且与 ADR 001/003 存在若干直接冲突（`[0u8; 256]` 违反 `;` 的纯分隔符定位、`~str` 违反可变性是绑定属性、基础类型表列出了 ADR 003 未承认的宽度）。核心目标：

1. 字面量的定型规则可由词法 + 局部上下文完成，不需要全局推断
2. 内置类型集合最小化，每个类型都有硬件或语义上的必要性
3. 消解与 ADR 001–005 的既有冲突，不新增脱糖规则

---

## 决定

### D1 — 整数类型：任意宽度 `u1..u64` / `i1..i64`，`i128`/`u128` 为特例

任意宽度整数是一等类型，直接对应硬件寄存器字段。`i128`/`u128` 保留但不属于任意宽度序列——它们跨越寄存器宽度，需要编译器生成多字运算。

```kore
enable   : u1  = 1
prescale : u3  = 0b101
addr     : u20 = 0x1_F000
wide     : u128 = 0xFFFF_FFFF_FFFF_FFFF_FFFF
```

**理由**: `u65..u127` 既无硬件对应也无实际需求，允许它们只会让后端多支持一批无人使用的宽度。

---

### D2 — 浮点类型：只有 `f32` / `f64`

删除 `f16` 与 `f128`。

**理由**: `f16` 的硬件支持在目标平台上不统一（需要 ARMv8.2+ 或 AVX512-FP16），`f128` 在多数平台要软件模拟。二者都可在需要时由库类型补上，不必占据内置类型位置。

---

### D3 — 整数字面量：四种进制，`_` 可出现在任意位置

```kore
0b1010_0101      -- 二进制
0o755            -- 八进制
1_000_000        -- 十进制
0xDEAD_BEEF      -- 十六进制

1_0_0            -- 合法，等于 100
0x_FF            -- 合法
```

`_` 不能作为字面量的首字符（那是标识符），其余位置一律允许，词法器直接跳过。

**理由**: 位置限制规则（如"不能紧跟进制前缀"）要额外的词法状态，收益只是拒绝一批无害写法。

---

### D4 — 类型后缀：直接拼接类型名

```kore
42i64            -- i64
0u8              -- u8
1.5f32           -- f32
0xFFu16          -- u16
1_000i128        -- i128
```

无分隔符、无特殊语法。词法器读完数字后继续读标识符字符，若结果是已知类型名则作为后缀。

**理由**: 不引入新记号；`42_i64` 式的下划线分隔与 D3 的任意位置 `_` 规则冲突。

---

### D5 — 转义序列：最小集 + `\x` + `\u{}`

```kore
"\n"        -- 0x0A
"\r"        -- 0x0D
"\t"        -- 0x09
"\0"        -- 0x00
"\\"        -- 反斜杠
"\""        -- 双引号
"\'"        -- 单引号
"\x1B[0m"   -- 精确字节
"\u{4E2D}"  -- 码点，展开为 3 字节 UTF-8

"\a"        -- 编译错误
"\e"        -- 编译错误
```

未列出的转义是编译错误，不是"按字面量处理"。

**理由**: `\a` `\b` `\f` `\v` 是终端时代遗产，`\x07` 更清楚。静默接受未知转义会把拼写错误变成运行期 bug。

---

### D6 — 反引号 = 原始字符串 + 多行；双引号不跨行

```kore
re := `\d+\.\d+`         -- 无转义处理

sql := `SELECT *
FROM t
WHERE x = 1`             -- 含真实换行

s := "未闭合             -- 语法错误：双引号不跨行
```

反引号内除反引号本身外无任何特殊字符，也没有转义机制。

**理由**: 一个记号一个含义——反引号唯一含义是"原样",不需要 `r"..."` / `"""..."""` 两套语法。双引号不跨行让词法器能在行末立刻报错，错误位置准确。

---

### D7 — 数组字面量类型是 `[N]T`，靠隐式借用转切片

```kore
a := [1, 2, 3]           -- [3]i32
s : []i32 = [1, 2, 3]    -- 先 [3]i32，再借用转 []i32

f :: (x []i32) => ...
f([1, 2, 3])             -- OK，临时数组活到语句结束
```

字面量本身永远是固定长度数组。转切片是借用转换，与 `buf[..]` 同一机制。

**理由**: 若字面量可直接是切片，就要回答"它的存储在哪"。定为 `[N]T` 后存储位置总是明确的（栈或 `.rodata`），生命周期规则复用既有的不逃逸检查。

---

### D8 — 不引入 `char`，`'a'` 是 `u8`

```kore
c  : u8 = 'a'            -- 97
nl : u8 = '\n'

-- '中' 编译错误：码点 0x4E2D 超出 u8

@ s.runes() => r {       -- r: u32
  ? r == 0x4E2D => ...
}
```

字符字面量是 `u8` 的书写形式。码点级遍历由库提供，产出 `u32`。

**理由**: `str` 是 UTF-8 字节序列，字节是它的自然索引单位。独立 `char` 类型会带来"`s[i]` 返回什么"的持续困扰，而底层代码（协议解析、词法器）操作的本来就是字节。

---

### D9 — 重复数组用 `[N]T{..v}`，复用结构填充

```kore
t := [256]u8{..0}
m := [4][4]f32{..[4]f32{..0.0}}
```

与结构体填充完全同形：

```kore
q := Vec3{x: 1.0, ..0}
```

**修正**: 撤销 ADR 003 中出现的 `[0u8; 256]` 写法——它与 ADR 001 冲突（`;` 是纯语法分隔符，parse 后消失，不能承载"重复"语义）。

**理由**: `..` 已有"其余字段填此值"的含义，数组只是字段名为下标的结构。不新增记号。

---

### D10 — `[]` 合法，但必须有目标类型

```kore
xs : [0]i32 = []         -- OK
f([])                    -- OK，从参数类型取
~ys : []i32 = []         -- OK

x := []                  -- 编译错误：无法推断
```

**理由**: 与 ADR 003 的双向推断一致——有目标类型就用，没有就报错，不引入"默认元素类型"这种兜底。

---

### D11 — 删除 `~str`

```kore
~s : str = "hello"
s = "world"              -- OK：重新绑定
-- s[0] = 'H'            -- 非法：str 内容不可变

~buf : [64]u8
buf[0] = 'H'             -- 可变文本走字节数组
```

**修正**: 删除 `docs/spec/03-types.md` 的 `~str -- 可变字符串视图`。

**理由**: ADR 003 定了可变性是绑定属性，`~^T` 是唯一的类型级例外（因为指针要区分"能否通过它写"）。`~str` 会开第二个例外，且它想表达的东西 `~[]u8` 已能表达。

---

### D12 — `nil` 既是类型名也是其唯一值

```kore
i32? ≡ i32 | nil

? r is {
  nil => log("none")
  n   => log(n)
}
```

**理由**: ADR 001 的 `T? → T | nil` 脱糖要求 `|` 两侧都是类型，所以 `nil` 必须是类型。同时它在模式和表达式位置都要能写，所以也是值。单值类型的类型名与值名同形不产生歧义——位置本身就区分二者。

---

### D13 — 不引入字符串插值

```kore
"hello, " + name         -- 拼接
fmt("hello, {}!", name)  -- 格式化
```

**理由**: 插值必然引入第二条脱糖规则（`InterpStr` → 拼接或 `fmt` 调用），突破 ADR 001 立的"只有 `T?` 脱糖"边界。且它要求词法器在字符串内部递归回调 parser，这是自举编译器里成本最高的一类词法-语法耦合。

---

### D14 — `usz` / `isz` 是独立 nominal 类型

不是 `u64` / `i64` 的平台别名。

```kore
n : usz = arr.len
m : u64 = n as u64       -- 必须显式
```

**理由**: 若是别名，同一份代码在 64 位平台编译通过、32 位平台报错。定为独立类型后 `as` 的位置在所有平台一致——可预测性优先于便利性（spec 01 取舍 1）。

---

### D15 — 逻辑运算用关键字 `and` / `or` / `not`

与 spec 01 关键字表一致。`!` 已被错误传播占用（`lookup(s)!`），不能兼任逻辑非。

---

### D16 — 单元素元组用尾逗号 `(x,)`，`()` 是 `void` 的值

```kore
t := (x,)                -- 单元素元组
p := (x)                 -- 就是 x，括号只是分组
u := ()                  -- void 的唯一值
```

**理由**: 零元组即单位类型，与 `void` 统一，不需要两个"什么都没有"的类型。

---

### D17 — 按位 AND / OR 用 `&` / `|`

```kore
flags & MASK
flags | FLAG_RW
a xor b
inv x
x rol 3
x << 2
```

`&` 在六记号体系里从未分配（取址是 `^x`，不是 `&x`）。`|` 的歧义可纯语法消解：联合声明的变体必须以 `.` 开头，所以 `|` 右侧有无前导 `.` 即可定性，parser 不需要类型信息。

**修正**: `docs/spec/01-overview.md` 的位运算行漏了 AND / OR，且理由写偏了——`xor` / `inv` / `rol` / `ror` 用词形的真正原因是 `^` 归指针、`~` 归可变，不是 `|` 被占用。

---

### D18 — 无类型字面量默认 `i32` / `f64`

```kore
x := 42                  -- i32
y := 3.14                -- f64

n : u8 = 42              -- u8，上下文优先
f(42)                    -- 按参数类型

big := 5_000_000_000     -- 编译错误：超 i32，需写 5_000_000_000i64
```

**理由**: 兜底类型只在完全无上下文时生效。超出兜底范围时报错而非自动升宽——自动升宽会让 `x := 5_000_000_000` 和 `x := 2` 得到不同类型，破坏可预测性。

---

### D19 — 字面量越界是编译错误，无例外

```kore
x : u8 = 300             -- 编译错误
y : u8 = -1              -- 编译错误

x : u8 = 300 as u8       -- OK，44
mask : u8 = 0xFF         -- OK
all  : u8 = inv 0u8      -- OK，255
```

`0xFF` 之类的掩码写法本就在范围内；需要全 1 时用 `inv 0u8` 表达意图。

**理由**: `-1` 作为"全 1"的惯用法在 C 里是常见 bug 来源。要求显式 `as` 或 `inv` 让意图出现在代码里。

---

### D20 — `.len` 是字段，不是方法

```kore
buf : [512]u8
buf.len                  -- 512，编译期常量

s : []u8 = buf[8..64]
s.len                    -- 56，运行期读字段

@ 0..arr.len => i { ... }
```

**理由**: 切片的运行期表示就是 `(ptr, len)` 两个字，`len` 是真实字段。数组的 `len` 是类型的一部分，编译期折叠为常量。写成方法会暗示有调用开销。

---

### D21 — 引入字节串字面量 `b"..."` → `[N]u8`

```kore
magic : [4]u8 = b"\x7FELF"
hdr := b"GET "           -- [4]u8

s := "GET "              -- str，UTF-8
```

`b"..."` 支持 D5 的全部转义，但 `\u{}` 除外（码点概念不适用于字节串）。

**理由**: 内核与 VM 代码常需嵌入协议头、魔数、固件 blob。没有 `b"..."` 就得手写 `[0x7F, 0x45, 0x4C, 0x46]`，可读性差且易错。它不是脱糖——词法器直接产出 `[N]u8` 字面量节点。

## 被拒绝的设计

| 设计 | 拒绝原因 |
|------|---------|
| 字符串插值 `"hi {name}"` | 引入第二条脱糖规则 + 词法器递归回调 parser（D13） |
| 独立 `char` 类型 | 与 `str` 的 UTF-8 字节索引语义冲突（D8） |
| `f16` / `f128` 内置 | 硬件支持不统一，可由库类型补（D2） |
| `u65..u127` 任意宽度 | 无硬件对应也无需求（D1） |
| `[v; N]` 重复数组 | `;` 是纯语法分隔符，不能承载语义（D9） |
| `~str` 可变字符串视图 | 可变性是绑定属性，`~^T` 是唯一类型级例外（D11） |
| `usz` 作为 `u64` 别名 | 同一代码在 32/64 位平台行为不一致（D14） |
| 字面量超范围自动升宽 | `x := 2` 与 `x := 5e9` 得到不同类型（D18） |
| `-1` 作为全 1 掩码 | C 遗留 bug 来源，改用 `inv 0u8`（D19） |
| `r"..."` / `"""..."""` | 反引号已覆盖原始 + 多行两种需求（D6） |
| `.len()` 方法形式 | 暗示调用开销，而切片 `len` 是真实字段（D20） |
